## DNS-pinned outbound transport (PR #293) — merged and deployed

PR #293 was merged into `main` on **2026-10-27** (merge commit `e92de4bcf7c3b9ad1f465d37262a6eaeb8457344`). Its `network-safety.js` source is identical on `main` and the current integration candidate (blob SHA `132071ffa2fd94967c0ac2a6616bd2b8e7cc9cf5`); `server.js` on main defaults `createApp` to `safePinnedFetch`.

The transport:
- Resolves and validates all DNS answers; rejects private, reserved, local, metadata and transition addresses, including mixed public/private answer sets.
- Pins the already validated IP address into the actual HTTPS socket's `lookup` callback while preserving the expected TLS `servername`.
- Requires HTTPS for remote destinations, permits HTTP only for explicit loopback development targets, blocks redirects by default, and respects abort/timeout while DNS is resolving.
- Is the default for the server's model-provider, Supabase REST/storage and integration request paths. The reviewed provider adapters receive the shared injected `fetchImpl`. The REA gateway's native `http.request` calls are constrained to `127.0.0.1` for its child process, not arbitrary outbound hosts.

**Source test evidence:** PR #293 Actions run [40529014426](https://github.com/ayaanraza2008/ULTRON-AI/actions/runs/40529014426) succeeded (both jobs). The test job ran **524 Node tests (523 passed, 0 failed, 1 skipped)** and 11 Python tests. `tests/network-safety.test.js` covers pinned socket lookup, mixed private/public DNS rejection, remote HTTP/redirect blocking, loopback development requests, abort and resolver timeout.

**Production revision evidence:** [Production revision run 40909211008](https://github.com/ayaanraza2008/ULTRON-AI/actions/runs/40909211008) passed on 2026-10-29 for expected main SHA `6b7f09d97508fc2be2085695d862a921e1ae8487`. Its log records three retries while Render served stale commit `47e011a86db8ced0d9edd7a881e98de3a085f048`, then a successful health/configuration/revision match once the deployed commit became `6b7f09d`. This demonstrates that the hosted Core service was serving the main revision containing the pinned transport at that check.

This does **not** constitute a live outbound provider-request smoke, prove every independent browser/runtime network stack uses the transport, or confirm infrastructure-level egress controls. Those remain separate checks; no deployment or production setting was changed during this review.
